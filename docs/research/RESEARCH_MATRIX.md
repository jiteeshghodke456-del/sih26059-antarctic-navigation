# Research Matrix — v3 §48A.31 compliance

This is the pre-implementation research matrix v3 §48A.31 requires and this repo did not
previously have as a single artifact. It is an **extraction**, not new research: every row below
was already answered somewhere in `docs/` or in the code, and this file's job is to point at
exactly where, say plainly what is still missing, and state what each finding changes about the
build. §48A.31's own table names **18 topic rows**, and as of 2026-09-07 this matrix covers all
18: **4 are SETTLED, 12 are PARTIAL, 2 are OPEN** — the open rows (navigation-stack integration,
human-factors validation) are genuine gaps with no prior work to cite, not oversights in this
extraction. Every row also now carries the two record fields §48A.31 requires and the first pass
of this file omitted: **conflicting sources** (explicitly "none identified" where that is the
honest answer, not a blank cell) and **confidence** (a plain high/medium/low with a one-line
reason, distinct from the row's overall SETTLED/PARTIAL/OPEN status — a row can be SETTLED overall
while individual sub-claims inside it carry different confidence levels, and several do).

Two companion files this matrix defers to rather than duplicates: `docs/research/
POLARIS_APPLICABILITY.md` and `docs/research/FORECAST_HORIZONS.md` did not exist in
`docs/research/` when this matrix's first pass was written, and were still absent when this
completion pass began. **Both appeared partway through this pass** (confirmed by a direct
filesystem check immediately after the pass started, and again once the 18-row table and the
first round of field additions were done) — so, per this task's own instruction, they are now
cited directly in rows 2, 3, 4, 5, 6 and 7 rather than left as a deferral. Row 3 (POLARIS) and
row 5 (Sea ice) absorb the most from them, since those are the two rows this matrix's own note
below originally named as deferred to these files by name; rows 2, 4, 6 and 7 pick up smaller,
more targeted findings the same two files happen to also settle. Nothing in either companion file
changes any row's SETTLED/PARTIAL/OPEN status — the additions sharpen and, in two cases (row 4's
loose end; ADR-025's stated reasoning, now in `docs/backlog.md`), close specific sub-questions
without moving a row's overall bottom line.

### Row 15 — multi-objective routing is built; "robust routing" is a different, unaddressed claim

Worth separating explicitly because the two halves of row 15's own topic label ("constrained
multi-objective formulation *and* robust routing") are not equally true. The multi-objective half
is real and specific: a 12-run dominance-filtered sweep over PolarRoute, named honestly as a
candidate set rather than a Pareto frontier (ADR-021), plus graded degradation instead of a hard
horizon cutoff (ADR-022). "Robust routing" in the sense v3 actually uses the phrase — a route
whose quality is evaluated across a *plausible range* of future ice/weather realizations, not just
one field — is a different and stronger claim, and nothing in this repository makes it: not the
design documents (a repo-wide grep for "robust," "scenario," and "plausible range" across every
`docs/*.md` file and the `isih/`/`models/` code returned no hit that addresses this sense of the
word), and not the code (`route_regret.py` backtests exactly one realized historical past per
departure date, and its own docstring names but never implements the ORACLE arm that would begin
to test a range). What exists instead — routing on a conformally-widened upper-confidence-bound
field — is a legitimate, real technique (it is D1, a genuine differentiator), but it is robustness
*to forecast uncertainty in magnitude*, not robustness *across a range of futures*. A judge who
knows the phrase "robust optimization" could reasonably ask for the second thing and be told,
honestly, that only the first exists. This is now recorded in `docs/backlog.md` rather than left
to be rediscovered.
